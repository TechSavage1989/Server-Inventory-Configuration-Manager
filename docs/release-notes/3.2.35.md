# Server Inventory and Migration Manager 3.2.35

Migration release. VMware VMs can be moved to a remote Hyper-V host or cluster from one admin computer with nothing installed in the VM, migration plans seed, sync, test and cut over many VMs on a schedule, and a new tool builds Hyper-V hosts and clusters from the recorded VMware environment. Replication change tracking no longer needs a full read at cutover as a precaution. Collection, reports, restore and settings are otherwise unchanged.

**Highlights**

- Move VMware VMs to a remote Hyper-V host or failover cluster from one admin computer, with nothing installed in the VM being moved, and migration plans that seed, sync, test and cut over many VMs on a schedule.
- Build Hyper-V hosts and clusters from the recorded VMware environment, with a preview of every change, and browse VMware and Hyper-V inventories in a tree of hosts, VMs, storage and networks.
- Replication change tracking no longer misses the storage that Windows shadow copies keep on the volume, so the last round before cutover does not need to read every used block as a precaution.

**Moving VMs**

- Move VMs can run on an admin computer: it connects to vCenter or ESXi and, over PowerShell remoting, to a remote Hyper-V host or failover cluster. Copies are written to the chosen node while the VM runs, and cutover creates the VM there and can add it to the cluster. Nothing is installed or started on the host.
- Prepare and fix up can run inside the moved machine from outside it, through PowerShell Direct on the Hyper-V host or PowerShell remoting, so no application is copied into the old server. Network settings are recorded from vCenter before each copy round.
- A VM whose files are encrypted only for its virtual TPM is no longer blocked. VMs with encrypted disks stay blocked and show the ways out.
- Migration plans (new tool, runs on the Hyper-V host): pick many VMs, seed them from a start time, keep them in sync on an interval, limit bandwidth, run a test cutover on an isolated copy, and cut over now or at a set time. One VM failing never stops the others. The scheduler runs while the application is open on that host.
- Guided migration shows one step at a time with Back and Next, marks optional steps, and can fix a blocked step in place. Every way of moving says when to pick it.

**Hyper-V hosts and inventories**

- Build Hyper-V hosts (new tool): drafts nodes, switches, VLANs, storage, cluster and witness settings from the VMware data and what you type. Preview changes nothing. Apply needs the plan name typed and a recent preview, only adds what is missing, and formats only blank disks.
- The Environment view for VMware and Hyper-V has a tree with Hosts and clusters, VMs and templates, Storage and Networking views, and a page with tabs for whatever is selected. Every name and count is a link.

**Replication**

- Change tracking treats the storage Windows keeps for shadow copies as empty space and reads every NTFS system file each round. The intermittent miss that led to the advice to tick Read every used block in the last round is fixed; the option stays as an extra check.
- Shadow copies (Previous Versions) that exist on the source are not carried to the copy.

**Requirements and limits**

- Windows x64, Windows Server 2012 or later, with Microsoft Edge or Chrome 109 or later, or the WebView2 Runtime. The Linux agent needs x86-64 and systemd.
- Remote Hyper-V moves support vCenter Server or ESXi 6.5 to 8.0 (not the free ESXi Hypervisor) to Windows Server 2012 R2 to 2025 with the Hyper-V module.
- Not yet field-tested: remote Hyper-V hosts and clusters, PowerShell Direct, building real Hyper-V nodes and clusters, long-running migration plans, and change tracking on a server that already holds shadow copies.
