# Server Inventory and Migration Manager 3.2.38

Migration fix release. Copies of running VMware VMs no longer stop on a missing ISO, changed-block rounds can read through VDDK, file shares can move between two other servers, and the interface scales to fit smaller windows. Collection, reports, restore and settings are otherwise unchanged.

**Highlights**

- Fixed: a VM whose CD or DVD drive still named a deleted ISO failed every copy round. Copies now eject CD, DVD and floppy images first (ticked by default), after recording each image path.
- Changed-block rounds of running VMware VMs can read only the changed blocks through VDDK, which you choose in Help > Settings.
- Move file shares can run on an admin computer and move shares between two other servers, and the interface scales its text and spacing with the window.

**Moving VMs**

- Eject CD/DVD and floppy images is ticked by default in New migration, Migration plans, Move VMs and the platform move. Each drive that names an image is set to a client device, not connected, after its image path is recorded. Without it, the error says how to fix it and the plan row offers a one-click fix. Readiness flags drives that name an image that is not connected.
- VDDK reads: VDDK's license does not allow it to be shipped with this application, so choose an extracted VDDK folder in Help > Settings. Every DLL in it must carry a valid Broadcom or VMware signature before anything loads. Rounds then open their own snapshot read only over NBDSSL and read only the blocks that changed. Without VDDK, or when it cannot connect, rounds read the datastore and then the snapshot export as before.

**New migration**

- VM names show again on tiles that carry the encryption note in What.

**File shares**

- New server: Another server runs the file share engine inside the new server through PowerShell remoting, so the new server copies straight from the old one with Robocopy. Files cross the network once and nothing is installed on either server.
- Keep copying until cutover repeats the copy every 15 minutes to 24 hours while the application is open. New migration offers Another file server with its own steps.

**Interface**

- Text and spacing scale with the window: full size at 2560x1369 and gradually denser down to 1920x1050 and below, never under 10.5 px text.

**Requirements and limits**

- Windows x64, Windows Server 2012 or later, with Microsoft Edge or Chrome 109 or later, or the WebView2 Runtime. The Linux agent needs x86-64 and systemd.
- Not yet field-tested: VDDK reads against a real ESXi host and vCenter, ejecting images on a real vCenter, and file share moves between two real servers over remoting.
