## Primary application baseline

- Maintain the Windows portable executable, Server-Inventory-Configuration-Manager.exe.
- The user-confirmed functional and visual baseline is Server Inventory & Configuration Exporter GUI v3.0.10.
- The original source ZIP's bundled EXE is byte-identical to the uploaded baseline. See docs/verification/baseline-verification.json.
- The v3.1.0 PS1 application was a mistaken product direction. It is historical only. Never use its UI, collector extraction, or build workflow as the executable baseline.
- v3.2.0 introduced executable updates. v3.2.1 restored direct original-source build inputs and hardened the updater. Maintain v3.2.10 or newer, including locked-target cleanup, guest browser isolation and profile-scoped shutdown.

The 2026-11-25 VMware migration features (VMware tab, Alt+6) are user-requested by an MSP moving VMware/ESXi estates to Hyper-V and Scale Computing HyperCore. `src/app/vmware_*.go`, `compare.go` and `src/app/Migrate-VmGuest.ps1` implement them; the Go core is untagged so `go test ./...` covers it on any platform, and `vmware.go` holds the Windows handlers. vCenter/ESXi is read through govmomi (pinned at v0.38.0, the last release whose go.mod allows Go 1.20). The only vSphere changes allowed are the opt-in Prepare source steps in `vmware_prepare.go` (remove all snapshots, guest shut down through VMware Tools, remove the virtual TPM, decrypt), run one VM at a time after the typed VM name, with a JSON record of the VM's state saved under LocalAppData `VMware\<server>\Prepare` before any change; never force power-off and never call any other changing method except replication rounds (`vmware_replicate.go`, phase 2): they may turn on changed block tracking when the operator allows it and create and remove only this application's own snapshot (`vmReplicaSnapshotName`, removed even when the round fails or is stopped), save a JSON record before each change, and refuse a VM with any other snapshot, an encrypted disk, an RDM or a snapshot chain. The first round seeds only the areas `QueryChangedDiskAreas("*")` reports allocated; later rounds copy only blocks changed since the change ID stored in the disk's copy record, falling back to a full hashed pass when tracking cannot answer. The simulator lacks `QueryChangedDiskAreas`, so tests replace `vmChangedAreas`. vCLS, vCenter/Photon appliances and nested ESXi get status `skip` ("Not moved"), are excluded from plans and waves, and Prepare refuses them. Full discovery (`vmware_discovery.go`, `vmware_discovery_report.go`, 2026-11-25, user-requested: "each individual host info as reported by vmware, as well as licensing") reads only properties and the read-only queries FetchSoftwarePackages, HostImageConfigGetAcceptance and QueryAssignedLicenses; a host that does not answer them gives one warning, never a failed read. License keys are masked to their first and last group (`vmMaskLicenseKey`) everywhere they are stored or shown. The runbook is written as HTML and Word (`Migration-Runbook.docx`, `vmware_docx.go`). The guest engine's SaveBitLocker mode writes recovery keys only to a file in the output folder (never the log) and suspends protection with `-RebootCount 0` before a vTPM is removed. The password stays in memory (`vmware.password`) until Forget or exit and never reaches logs, files, state responses or settings. TLS uses system roots first; an untrusted certificate is refused with its SHA-256 thumbprint and accepted only when the operator trusts that exact thumbprint, for the session. Relationships (2026-11-25, user-requested: VMs per host, disks per datastore, adapters per network) come from `vmRelationsFor` in `vmware_relations.go` for the discovery report and from `vmRelations` in `index.html` for the Environment view's Browse panel; keep the two matching (datastore and network names are matched per datacenter, then by name), keep host bodies built only when opened so large estates stay fast. The Environment view's details panel (`#vmDrawer`, 2026-11-25, user-requested: "everything should be linked and interactive") opens any VM, host, cluster, datastore, network or license; build every name in it and in Browse as a link through `vmRefLink`, and keep the readiness cards counted from the VM list so they add up to All VMs (system VMs count as Not moved), and keep datastore `hosts` optional because older saved inventories lack it. Readiness rules live in `assessVM` and are re-run when a saved inventory is opened. The disk copy engine (phase 2, `vmcopy_*.go`) writes dynamic VHDX files itself (`vmcopy_vhdx.go`, MS-VHDX, 32 MB blocks, empty log, zero chunks left unallocated) and copies in 4 MB chunks with each chunk's SHA-256 in `<target>.copy.json`: a stopped copy resumes, a repeat run is a delta pass that rewrites only changed chunks, changed-block ranges limit what a pass reads, and verify reads the VHDX back against the hashes. It never overwrites a file it did not create or a copy of a different source. Sources are local flat VMDKs or raw images and datastore files read over the vSphere `/folder` HTTPS interface with GET/HEAD Range requests only; snapshot deltas, sparse/SEsparse disks and RDMs are refused with the reason (conversion is phase 4). Copies go to a `vmCopySink`: `vmLocalSink` (VHDX plus record on this computer) or `vmRemoteSink`, which sends chunks to a receiver (`vmcopy_receiver.go`, phase 2 step 3) on the target host over HTTPS. The receiver writes only plain `.vhdx` names inside its one folder, makes a new self-signed certificate and 20-character pairing code each start, and checks every chunk's SHA-256 before writing; zero chunks travel as a hash only, one sender per disk at a time (an idle sender's session can be taken over after two minutes), and a stopped receiver saves records so a new one resumes. The sender pins the receiver's exact certificate thumbprint (no CA, no proxy) and sends the code with each request; never log the code or relax the pin. The in-guest source agent (`vmagent.go`, `vmagent_windows.go`, phase 2 step 4) copies a disk of the computer it runs on (any hypervisor, or physical for P2V): each NTFS/ReFS volume is read from a new Volume Shadow Copy (`Win32_ShadowCopy.Create`, deleted when the source closes, only IDs it created), everything else from `\\.\PhysicalDriveN`; spanned volumes are refused, and copying a volume live without a shadow copy needs `allowLive`. Shadow copies are per volume, not one set across volumes. `TestAgentCopiesALiveDiskThroughAShadowCopy` proves a write made after the shadow copy stays out of the copy. `TestWindowsMountsCopiedVHDXWithIdenticalContents` mounts a copied VHDX with Windows and compares the bytes. Encrypted VMs must be decrypted before any copy. Plans are saved per server under LocalAppData `VMware\`; reports and CSVs go to the output folder, CSV cells are formula-neutralised. The guest engine (PowerShell 3.0) logs with `[Console]::Out` (never `Write-Output`, which pollutes return values), saves adapter settings before Apply so Undo works, refuses items not in the capture or no longer present, never touches boot/system disks, and refuses VMware Tools removal while still on VMware. Changing guest modes need the typed computer name (server-checked). Before/after comparison reads two collection packages and writes outside them (never into a package, whose manifest restore verifies). Every VMware step is a critical operation that blocks collection, restore, migration, update install and closing. `scripts/Test-VmGuest.ps1` (CI job `vmguest`) runs a real loopback-adapter round trip; `scripts/test_workspace.cjs` covers the tab with synthetic data. Targets (2026-11-25, user-requested: "moving to nutanix, and honestly options for any potential migration, including Virtual to physical") are profiles in `vmware_targets.go`: Hyper-V, Scale HyperCore, Nutanix AHV, Proxmox VE, Azure, Amazon EC2 and Physical server (V2P). Add a target there (drivers, firmware, TPM, shared disks, passthrough, USB, tool, sizing kind) rather than with `if target ==` branches; the UI's `vmTargetList` and `#vmTargetSelect` must list the same IDs. Cloud targets size by quota and physical by server, so the cluster fields are hidden for them. The guest engine's `Get-TargetChecks` reports one driver check per target ID and `Get-Platform` names the current platform for any source; never relax the refusal to remove VMware Tools while still on VMware.

## Repository standards (all contributors and AI tools)

This repository follows the shared TechSavage1989 standard in [`docs/REPOSITORY_STANDARDS.md`](docs/REPOSITORY_STANDARDS.md), the same file in every app repository. Read it before changing anything. In short:

- **README:** centered header (real icon, one `<h1>`, tagline, quick links Download · Get started · Features · Screenshots · Updates · Development, hero image), then the standard section order. Update it in the same pull request as any user-visible change.
- **Screenshots:** real captures with fictional data in `docs/images/` (`hero.png` + kebab-case names). Recapture any screenshot a UI change makes stale, in the same pull request.
- **Layout:** compact root; respect the root allowlist and checks above. Never commit build output, binaries, archives, logs, caches or secrets.
- **Branches:** short-lived `feat/` `fix/` `docs/` `chore/` `release/` branches, one focused change per pull request, merge only on green checks, delete the branch after merging.
- **Instructions:** this file is the single source of project rules for every tool; `CLAUDE.md` imports it. Add new rules and gotchas here.

The update feed and in-app update banner show the first three `- ` bullets of `docs/release-notes/<version>.md` verbatim as plain text, so keep those three bullets free of Markdown emphasis or code formatting.

README application screenshots in `docs/images/` are captured from the real `src/app/index.html` with the production CSP and synthetic `/api/state` responses at 1440 px wide (1000 px tall unless the existing image is shorter). The interface switches to its compact layout (no hero/version row, no update notes) at 720 px of height or less, so use at least 760 px when those should show. `report-executive-summary.png` is the published release's `Report-Preview.png` (real renderer, synthetic data); refresh it after each release that changes the report.
